# 关于「3.6 后端统一」「跟随玩家信息的附加 map 通道」「直接加字段」的看法

（写给 Kaleidoscopic 作者；结论基于我读到的当前实现：V7 协议用 `PacketId` 区分消息、
`PlayerSnapshot` 是 23 个位置参数的固定构造并已携带可变长 `WireBytes shieldData`、
MPCC 是「按需拉取 + 图集缓存淘汰」的资源流。）

---

## 0. 先摆一个判断标准

判断"某种通道该不该做"，先看数据的**语义属性**，它们决定可靠性与调度策略：

| 数据 | 例子 | 频率 | 大小 | 可丢？ | 需要缓存？ |
| --- | --- | --- | --- | --- | --- |
| **状态流** | 玩家/实体位置、动画帧、血量 | 每帧(60Hz) | 几十~几千字节 | 可丢（下一帧会补） | 不需要（只留最新） |
| **资源流** | MPCC 的图集/贴图 | 按需 | 几 KB~几 MB | 不能丢 | 需要（含淘汰/预算） |
| **事件流** | 一次性动作、伤害结算 | 触发时 | 小 | 有些不能丢 | 不需要 |

KIC 现在需要的是**状态流**（每帧的小负载，可以丢帧、下一帧补上）。这一点决定了下面三个方案的取舍。

---

## 1. 关于「3.6 重构后端统一」

要区分两种"统一"：

### 1.1 值得做：**传输/编解码/调度分层统一**

如果 3.6 指的是"所有消息走同一套 Dispatcher + `IProtocolMessage/PacketId` 注册表 + 版本协商 + 背压/统计"，
我的看法是**推荐**，理由：

- 新增一类数据只需注册一个 `PacketId` + handler，不必碰已有消息的编解码（现在 V7 已经是这个形状，
  继续沿用成本最低）；
- 版本协商、限流、统计、诊断窗口能集中一处，出问题只看一层日志；
- 正好可以把下面第 2 节说的"附加通道"做成框架的一部分，而不是又一次特例。

### 1.2 不建议：**把状态流与资源流合并成一种机制**

如果 3.6 指的是"把 PlayerInfo 这类逐帧状态与 MPCC 这类资源拉取统一成同一套通道"，我会**反对**：

- 两者的可靠性/延迟/缓存需求相反：状态流要"低延迟、可丢、永远只保留最新"，
  资源流要"不丢、可分片、要缓存与预算淘汰"。硬统一后两边都会被对方的策略拖累
  （状态流被缓存/排队拖慢，资源流被高频小包污染缓存与统计）；
- MPCC 现在有 Sources / Requests / AtlasLoader / GPU Job / CacheBudget 一整套，
  这套结构对小状态包是纯负担；
- 调试成本：一个管道里混两种失败模式（丢包 vs 缓存淘汰）会很难定位。

**推荐分层**：传输层（QUIC/Datagram、批处理、压缩）→ 消息层（PacketId、版本、TLV 扩展）
→ 语义层（状态流 / 资源流 / 事件流各自独立）。KIC 要的东西属于**消息层的通用扩展点**，与语义层解耦。

---

## 2. 关于「跟随玩家信息的附加 `map<string, byte[]>` 注册」

**这是三个方案里我最推荐的**，但建议做成"消息层的注册表"，而不是写死在 `PlayerSnapshot` 里。

两种落法：

| 落法 | 优点 | 缺点 |
| --- | --- | --- |
| **A1. 挂在玩家快照上**（`PlayerSnapshot` 增加 `Dictionary<string, WireBytes> extras`，或一个 TLV 块） | 改动集中；天然跟着玩家生命周期与频率走；一次序列化一次发送 | 每次快照都要带（小负载无所谓，但要给每 key 配额）；`PlayerSnapshot` 已 23 个位置参数，继续加会让构造爆炸（建议顺手改成 builder/可空 extras） |
| **A2. 独立消息类型**（新增 `PacketId`，按 `playerToken → map<key, bytes>` 同步，频率/优先级独立） | 与核心玩家快照解耦；扩展数据可独立限频、独立丢包策略、独立版本；新增 key 不动核心协议 | 多一个消息类型与一套调度；需要自己处理"玩家离开/切房"清理 |

**建议**：如果你的目标是"让第三方 mod 能自助挂数据"，选 **A2**；如果只想最小改动先跑通，选 **A1**，
并在 3.6 统一消息层时迁移到 A2。无论哪种，下面这几条是必须的：

1. **key 命名空间**：`"<modid>.<channel>"`（例如 `kic.state` / `kic.fx` / `kic.hitbox`），避免冲突；
2. **每 key 自带版本**：核心只负责透传字节，内容的演进由 key 自己负责（KIC 的负载里已经有 version 字节）；
3. **字节配额 + 限流**：给每个 key 一个每帧上限（例如 4KB）与总量预算，超限丢弃并计入统计
   （否则一个 mod 的 bug 会拖垮整条链路）；
4. **未知 key 的处理**：没注册该 key 的客户端直接忽略（保证"别人不装这个 mod 也不报错"）；
   可选：握手时交换已注册 key 集合，让发送端知道对方是否支持（省掉无效流量）；
5. **生命周期清理**：玩家离开/换房间时丢弃其 extras 缓存，并提供 `OnPlayerRemoved` 回调；
6. **写入时机**：允许"无变化时不写"（KIC 空闲时负载本来就只有 47 字节，可以进一步降到 0）。

一个接口草案（形状示意，不必照抄）：

```csharp
Kaleidoscopic.Api.RegisterPlayerExtraChannel(
    key:            "kic.fx",           // 命名空间
    version:        5,                  // 通道自带版本
    perFrameBudget: 4096,               // 超限丢弃本次并记统计
    priority:       Priority.Low,       // 可丢、可合并
    write:          (PlayerContext ctx, BinaryWriter w) => { /* 写负载 */ },
    onReceive:      (PlayerContext ctx, BinaryReader r, int ver) => { /* 读负载 */ },
    onPlayerRemoved:(PlayerContext ctx) => { /* 清理 */ });
```

## 3. 关于「添加新的字段」

**适合**：核心通用、稳定、所有 mod 都可能关心的属性。比如把一个正式的
`avatarKind`（0=诺艾尔 1=小骑士 …）加进 `PlayerSnapshot`，比现在 KIC 借 `characterTitle` 字符串判断要稳，
也让别的模组受益。

**不适合**：某一个 mod 的私有负载。原因：

- 每次加字段都要改 `PlayerSnapshot`（23 个位置参数）+ 编解码 + 收发两侧兼容策略，
  协议一动就要考虑"老客户端收到未知字段会不会错位"；
- 不可扩展：KIC 现在已经借用了 10 个字段（`characterTitle`、`caneName`、`poseTitle`、
  `frameIndex`、`aimInt`、`nameColor`、`ay`、`curMgKindInt`、`skillMpHold`、`curMgReduceMp`）
  外加 `shieldData`；再来的 mod 只能继续借，字段语义会越来越混乱。

**结论**：核心通用状态 → 加正式字段；mod 私有负载 → 走第 2 节的附加通道。

---

## 4. 关于「直接转发的 mpcc 同信道」

从数据语义看，**MPCC 这条通道不适合逐帧小状态**，但**非常适合静态资源**：

| 用途 | 建议 |
| --- | --- |
| KIC 的每帧状态/特效负载（≤2.5KB，60Hz） | 走第 2 节的附加通道（可丢帧、可降频、可与输入合并） |
| KIC 的**精灵帧素材**（2005 张 PNG，现在靠"两端资产集必须一致 + 下标"耦合） | **就地复用 MPCC 的思路**：发送端注册"帧资源提供者"，接收端缺帧时按需拉取 → 进本地缓存 |

为什么后者是 MPCC 的正确用法：它本来就是 Sources / Requests / AtlasLoader / 缓存预算那一套，
天然支持"按需、可缓存、可淘汰、可失败重试"。**如果 KIC 想彻底摆脱"两端素材必须逐字节一致"，
这是唯一干净的路**（现在的痛点：一台机器缺一帧图，远端就整帧不画或画错）。

---

## 5. 给 KIC 侧迁移的对应关系（供参考）

如果第 2 节的附加通道做了，KIC 会把现在的借用字段迁成三个 key：

| key | 内容 | 频率 | 备注 |
| --- | --- | --- | --- |
| `kic.state` | 精灵名/剪辑/帧号/朝向/脚底 Y/血量魂量 | 每帧（无变化不发） | 对应现在借的 8~10 个字段 |
| `kic.fx` | 特效四边形 + 下砸/挽歌/孢子/法阵语义段 | 每帧，可降频到 20~30Hz | 现在塞在 `shieldData` 里的主体 |
| `kic.hitbox` | 骨钉攻击判定箱（拼刀判定） | 挥砍期间高频、其余不发 | 对延迟敏感，建议独立优先级 |

过渡期建议"双写"：新通道 + 旧字段并存，对端不支持新通道时自动退回旧路径，
这样老客户端不会因为升级而互相看不见。

---

## 6. 我的结论（一句话版）

1. **3.6 值得做**，但只统一"传输/消息层"，不要把状态流与资源流合并；
2. **附加 `map<string,byte[]>` 通道是正解**，建议做成消息层注册表（独立 `PacketId` 或挂在快照上），
   必备：命名空间 key、每 key 版本、字节配额、未注册即忽略、离开清理；
3. **直接加字段只留给核心通用属性**（例如正式的 `avatarKind`），mod 私有负载一律走附加通道；
4. **MPCC 同信道**用在"静态资源按需拉取"上（能解决素材一致性的老问题），不要用来传逐帧状态。
